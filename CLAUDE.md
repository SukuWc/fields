# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # Install dependencies
npm start          # Start dev server (Vite, hot reload, typically http://localhost:5173)
npm test           # Headless AMR coupling checks (node test/amr.test.mjs)
npm run build      # Production build, Vite base /fields/ (output: dist/). PR previews set VITE_BASE_PATH.
```

## Dependency notes

`planck-js` is intentionally pinned at `^0.3.31`. The newer `planck` package (v1+) has breaking API changes and requires a `stage-js` peer dependency that is incompatible with `planck-renderer@2.2.0` (already at latest). Do not upgrade `planck-js` or `planck-renderer` without significant migration work.

## Architecture

This is an interactive web sailing simulator combining 2D fluid dynamics with 3D rendering.

### Simulation Loop

`loop.js` `FixedStepLoop` ticks at 30 Hz: `world.step(1/30)`, then in `main.js`: camera follow (`view.update()` on the last frame's `boat0`), `host.tick({ dt, held, present, view })`; the host does `world.step`, `sim.step` and `presentStep` and hands back a plain frame (compact scene `state` incl. the HUD values `state.hud`, `statics` when they change), from which main.js builds guides, body outlines and the readout / HUD panels (`buildScene`). Nothing drawn or shown is built on the host: pair overlays travel as `rules.js` `pairStateFor` (boat ids and rule codes, built by `pairGuidesFromState`), penalty badges, incident reasons and finish labels as codes (`rule-text.js` writes the text; format in `host-protocol.js`, "Rule data"). `Sim.step` (sim.js), in order:
1. scenario frames f..f+2 (`SCENARIO_FRAMES_PER_TICK` = 3)
2. held boat commands (helm, heading target) from `controls.js` `heldCommands()`
3. `boat.physics_model_step()` per boat + boat→fluid energy
4. marks, start sequence, course progress, finish, race bots, leaderboard (world-step work)
5. per-boat rules readout capture, boundary, `evaluateAllPairs`, `recordContacts`, `recordMarkTouches`
6. AMR tracking, `bm.advance_frame()` (lattice)
Three.js renders separately at ≤ 30 fps (`renderer.js`).

In dev mode the loop still runs scenarios, keys, boats, and the camera, but it does not apply boat→fluid energy, does not move AMR domains, and does not call `bm.physics_model_step()`. See Dev mode below.

### Module responsibilities

- **`sim.js`** (`Sim`) owns: `players[]`, `marks[]`, `course`, `startSequence`, `raceResults`, `raceBots`, `boundary`, `leaderboard`, `rulesTime`, the scenario frame counter and its own rules state (`rules.js` `createRulesState()`; `sim.activate()` / `useRulesState` makes it the one rules.js and mark-touch.js read). Commands: boat `helm`, `headingTarget`, `autopilot`, `tack`, `penaltyTurn`; admin `restart`, `wind`, `devMode`, `barrier`, `options`, `simRes`, `amrMode`, `cellBudget` (`{ tune, target }`). Events (`sim.on`, `drainEvents`): `view` (scenario camera hints), `bindControls`, `cleared`. `snapshot()` is plain JSON data. No DOM or three.js: `test/no-dom.test.mjs` runs every scenario headless.
- **`host.js`** (`SimCore`, `LocalHost`) owns `bm`, `map`, `sim`, the field painter and plot options. The client sees only `host.info`, frames (`onFrame`), events (`on`; `bindControls` carries `boats`), `command()` results (`restart` → scenario card, `simRes`/`amrMode` → `{ rebuilt, lattice }`), `query()` (field velocity / wind at a point) and perf stats. `test/host.test.mjs` checks LocalHost against a bare Sim and that everything crossing is structured-cloneable.
- **`main.js`** (client) owns: `dataTextureMaterial`, `view`, the loop (time only), `currentGuides`. Passes a `() => ({ bodies, guides, devMode })` getter to `renderer.js`; the renderer no longer walks the planck world.
- **`renderer.js`** owns: `camera`, `scene`, `renderer`, `polygons[]`, `arrows[]`. `initRenderer(map, planeMat, view)` must be called before `setupControls` (controls needs `getCamera`).
- **`controls.js`** owns: `key_bind_list` (key → command), `key_state`, the scenario card. Scenario definitions are in `scenarios.js`.

### Boltzmann Fluid Engine (`boltzmann.js`)

Uses the **D2Q9 lattice** (9-velocity 2D LBM). Key classes:

- `SimulationCell` — single lattice node. Fields match paper notation: `f0, fN, fS, fE, fW, fNE, fNW, fSE, fSW` (post-collision populations), `fN_in … fSW_in` (incoming buffers), `rho`, `ux`, `uy`, `curl`. `recomputeMacros()` refreshes ρ and u from the populations after streaming or a grid transfer.
- `Boltzmann` — top-level class. Owns `cells[]` (all cells), `interiorCells[]` (interior nodes not covered by a child), `_allInteriorCells[]` (every interior node, including covered ones), and the `collideAndStream(cells, omega)` helper that runs one full LBM step (collide→stream→bounce→consolidate) on any cell array. Step order in `physics_model_step`: collide → stream → bounce → consolidate → `setBoundaries` (boundaries enforced after propagation, per paper). The coarse step runs on `_allInteriorCells` so a pull from a covered neighbour sees post-collision populations; `averageToCoarse` then overwrites the covered nodes.
- **Adaptive mesh refinement** is multi-domain (`RefinementDomain`). The rectangle is a reusable window; a per-cell mask (`setDisk`) refines a circle rasterized on the parent lattice. Diagonal-only 2×2 contacts are closed so every interface edge has a neighbour for the existing 1D cubic. Edge ghosts (one axis half-integer, or a coincident node just outside) and corner ghosts (both axes half-integer) are the overlap: coupling from the rectangular scheme runs on that staircase. Each level runs two sub-steps per parent step (convective scaling, ratio 2). `omega_f` follows Eq. 24. Coarse→fine coupling rescales non-equilibrium populations (Eq. 29) with cubic spatial interpolation (Eqs. 38/39) or a direct copy on coincident nodes (Eq. 34). Fine→coarse restriction takes ρ and u from the coincident fine node and filters only `f_neq` on the centered D2Q9 stencil (Eq. 33), then rescales (Eq. 30). Ghost boundaries interpolate ρ, u, and `f_neq` between the two parent time levels (§3.5). A window moves with `shiftDomain` / `shiftBy`: one parent cell at a time, in place, restricting cells that leave and carrying nested domains with it. `main.js` recenters a window when the boat is more than one cell from its center. Level 2 is a smaller disk inside level 1. Overlapping boats: the refined region is the union of the masks; the finest level writes the parent node and is what sampling and sail forcing read; the same level, the later domain wins.
- **AMR reference paper**: Lagrava, Malaspinas, Latt, Chopard — *"Advances in multi-domain lattice Boltzmann grid refinement"*, J. Comput. Phys. 231:4808–4822, 2012. DOI: 10.1016/j.jcp.2012.03.015. PDF at `research/lagrava_gr_2012.pdf`. This is the paper the multi-domain coupling follows (cell-vertex, convective scaling, Dupuis–Chopard non-equilibrium rescaling).
- **Debug visualisation**: `RefinementDomain.worldBorderLines(bm)` returns a smooth circle for that boat's disk (four rectangle segments when no disk is set). The light staircase (`0x9ad0ff`) is the outer boundary of the union of every mask at that refinement level (`unionMaskBorderLines`): overlapping boats share one outline, and boats that do not touch keep a separate island. Level 1 and level 2 are drawn separately. Nested circles convert each parent axis with that axis's root origin (`cx0_root` / `cy0_root`); using the horizontal origin for both axes draws the inner disk away from the boat. `main.js` pushes guides after the windows move, so the circles match the boat on that frame. `trackBoats` pairs each boat with its own window, so a skipped boat does not leave an index hole the next boat's domain falls into.

### Boat Physics (`boat.js`)

Each `Boat` instance:
- Has hull, rudder, mainsail, and jib represented as Planck.js bodies/fixtures
- Computes aerodynamic forces via pre-computed lift/drag curves (look-up tables in `docs/`)
- Has an **autopilot** with heading PID-style control (`autopilot_heading`, `autopilot_active`)
- Queries `map.get_wind(x, y)` each step. That is the only wind seam: it returns `{ speed, direction, vx, vy }` from whichever provider is active (`FluidWind` or `ConstantWind`)

### Simulation resolution (`#simRes`, `?simRes=2|4`)

Settings select: Default (1 root cell = 1 world unit), x2 coarser (2 units), x4 coarser (4 units). A change calls `bm.setResolution(1/k)` (root lattice rebuilt in place, same `bm` object everywhere), `resetTracking` (drops AMR windows and field-island state), resizes the field plane to `bm.latticeWorldWidth` (the map rounded up to whole cells: 76 units at x2/x4), and clicks Restart.

- **Scaling**: lattice U (= UI wind / 100) and ν stay fixed. The root grid takes `bm.stepsPerFrame = resolution` steps per frame (`advance_frame`, one step every 2nd / 4th frame). Δx and Δt both grow by k, so physical velocity, TWS, `get_field_velocity` units and advection speed in world units per frame are unchanged, and Mach / stability margin are the Default ones. Tradeoff: physical viscosity ν·Δx²/Δt is k× higher (Reynolds k× lower): smoother, shorter wakes; the field also updates every k frames.
- **Viscosity**: `bm.matchedNu = 0.025·resolution` is Default's physical ν on a k-unit cell. Level 1 builds ω_f from it (Eq. 24), so the boat stack and field islands run at Default's ω for their cell size. The root keeps ν_lat ≥ `ROOT_NU_FLOOR` (0.025): plain BGK at 0.0125 diverged on the x2 barrier at wind 25. So only the unrefined root stays k× more viscous; Eq. 29/30 (τ_f/2τ_c) maps strain rate across that jump.
- **Sail**: lattice momentum per frame is `SAIL_LATTICE_COUPLING × resolution²` (a root cell holds k² world units), so physical momentum per frame matches. Kicks on non-stepping frames stay on the populations / `pendingInjections`.
- **AMR**: the boat stack always reaches 1/8-unit cells. `amrParams(bm).levels` is the Default three (cells ½ / ¼ / ⅛, R 8 / 4 / 2 world units) preceded by log2(k) outer rings: x2 adds cell 1, R 12; x4 adds cell 2, R 20 and cell 1, R 12 (4 own cells of buffer each, window half R + 12, cap ≈ disk + 60 %). Every level is a disk floor plus curl growth/erosion inside its parent's mask; `trackOne` nests them in a loop. Field islands stay one level below the root. Curl is normalised by world spacing; hold, seed size and caps scale with k; windows may slide up to k cells per tracking call (tracking runs on stepping frames). Texture oversampling is 8k so the finest cell keeps one texel. Default values are the original constants.
- **Sampling**: on a coarse grid `get_field_velocity` is bilinear in the continuous cell coordinate; Default keeps the original lookup.
- Tests: `test/sim-res.test.mjs` (harness in `scripts/sim-res-harness.mjs`); perf table: `node --import ./test/register.mjs scripts/sim-res-check.mjs`.

### Wind seam (`wind.js`, `map.js`)

Boats never sample the lattice. `Map.get_wind(x, y)` delegates to the active provider:

- `FluidWind` — averages `bm.get_field_velocity` over a ±2 world-unit stencil (the historical `Map.get_wind` body). `vx`/`vy` are lattice velocity / 4. `speed` is true wind in m/s, `|v| * 400 * WIND_UNIT_MPS` (0.3). The boat keeps its internal `wind_speed` in the old units (`|v| * 400`, = m/s / 0.3) so the sail model is unchanged; telemetry `tws` is m/s. `direction` is `atan2(vy, vx)` in degrees + 180.
- `ConstantWind` — the same vector at every position. Constructed from the `wind_angle` and `wind_speed` constants at the top of `main.js`. For a given angle and speed it matches `FluidWind` on a uniform field, so boats feel the same force in both modes.

`direction` is where the wind **comes from** (0 = from +X, 90 = from +Y). `(vx, vy)` points **downwind**, which is the lattice flow and the direction sail drag pushes the boat. Wind indicators (the dev-mode arrow and the per-boat true-wind ticks) point downwind. The dev-mode banner prints both: `from 90° to 270°`.

`Map.setDevMode(on)` selects `ConstantWind` or `FluidWind`. `Map.setWindProvider(provider)` installs any object with `getWind(x, y)` and is reset the next time `setDevMode` runs.

### Dev mode (constant wind)

Dev mode is for working on a racing-rules engine without the fluid sim's cost or variability. Boats, autopilot, scenarios, camera, and physics-body rendering keep running. The fluid texture plane is hidden. A cyan arrow follows the camera and points downwind; the banner states where the wind comes from and where it blows.

Turn it on either way:

- **Dev mode** checkbox at the top of the `#settings` panel. Fluid-only controls (mesh refinement, barrier, boat energy, plot sliders) are disabled while it is on; their checked state is kept and applies again when dev mode is turned off.
- URL query `?devmode=1` (also `true`). Every settings control in `#settings` (checkboxes, number and range inputs, and the plot dropdown) is mirrored into the query string by `installUrlSettings`: the ids of `src/settings-registry.js` (`urlSettingIds`; in a server room minus the room-scope settings, the Room settings panel `#admin_panel`, whose values come from the server). Defaults come from the registry too (`settings-panel.js applySettingDefaults`), not from the markup: only non-default values are written, via `history.replaceState`. The dev-mode checkbox uses the existing `devmode` name — `devmode=1` when on, omitted when off. On load the query is applied by setting each control and dispatching `input`/`change`, so the same handlers run as a user edit. **Reset settings** restores the captured defaults and drops those params. Unrelated query keys are preserved.

Defaults are `wind_angle = 90` (from +Y, blowing toward −Y) and `wind_speed = 15` in `src/main.js`, the same inlet wind the lattice is initialized with. The **Wind angle** and **Wind speed** inputs edit the live `ConstantWind`. Wind angle still writes `bm.direction` (UI angle + 180), as before. Wind speed writes `bm.speed` as `value / 100`, so the fluid inlet matches if you leave dev mode. The lattice is still constructed and initialized at startup so leaving dev mode resumes the field that was already there; it is just not stepped while dev mode is on.

`get_field_velocity` clamps its bilinear sample to the lattice. The ±2 world-unit stencil used to read `undefined.ux` once a probe crossed the north edge or either negative edge (positive x past the last column wraps into the next row and returns a wrong cell instead of throwing). In-range samples are unchanged.

### Coordinate System

- World space: centered at (0,0), ±`map_w/2` × ±`map_h/2`. Map size (`src/map-size.js`, `#map_size` select, `?map_size=50x100|100x200|200x400`, default `100x200`; legacy `?mapSize=75|150` still loads the old squares): width × length in m, length along the wind (Y). Changing it reloads the page (drops `?simRes`). Walls 2 m inside the edge (`WALL_INSET_M`). Each size sets the default root cell: 50×100 and 100×200 at 1 m, 200×400 at 4 m (x4), so the field costs about 13–16 ms per frame on the box vs 12.5 ms on the old 75 m map; the boat refinement stack does not depend on the map. Scenarios keep their fixed world coordinates (built for the 75 m square); `SCENARIO_EXTENT` gives their half-extents, `fitMapSize` picks the smallest size that fits, so course scenarios 12–17 (±34 m across the wind) load on 100×200 when 50×100 is asked (selecting one in the app reloads). The two stray `map.js` circles stay at (0, 14.5) and (0, 20). Camera pan limits keep a 7.5 m margin; zoom-out (`cameraLimits`) shows the whole length and the camera far plane follows it; zoom steps grow above zoom 30. Check: `scripts/map-size-check.mjs`.
- `bm_resolution` (default 2) scales the LBM grid: `map_w * bm_resolution` cells per axis
- Texture oversampling (default 4) further upscales for smoother rendering

### Scenarios

Scenarios are defined in `src/scenarios.js` (`buildScenarios(sim)`; state such as `marks[]`, `course`, `startSequence` is on the `Sim`, the old `controls.js` getters are gone) as sparse arrays indexed by physics frame number. Scenario 0 = single boat autopilot; 1 = two-boat race; 2–4 = multi-boat automated sequences; 5 = empty template. 11 = one boat on close-hauled autopilot hitting an anchored mark (physics only). Marks live in `controls.js` `marks[]` (`getMarks()`), separate from `players[]`, so the rules engine never sees them; `main.js` calls `mark.physics_model_step()` once per world step (spring `MARK_SPRING_K`, damper `MARK_DAMPING`). 12 = anticlockwise triangle course, one boat, every mark to port. `controls.js` holds the active `course` (`getCourse()`); `main.js` calls `course.progressFor(boat).update(x, y)` once per world step and draws `courseGuides` for boat 0. The bearing from the mark to the boat is integrated inside the 12 m zone, signed by the rounding side, from the incoming ray (toward the previous mark). The mark is *rounded* (course progress, `progress.target` / `targetIndex` = first unrounded) at the midpoint ray, `roundedDeg` = (180° + turn) / 2, with 5° hysteresis. The *highlight* (`progress.display` / `displayIndex`) stays on a rounded mark until the outgoing ray (`nextLegDeg` = 180° + turn) or until the boat leaves the zone. The overlay is minimal: pulsing ring + `NEXT n · port` (or `✓ n`) on the highlighted mark, its faint 12 m zone, one short dashed amber line along the midpoint ray, grey `✓ n` on marks rounded in the current (target's) lap (`roundedMarks()`), and the dashed course line. No check-angle numbers are drawn. See the header of `course.js`. 13 = windward-leeward: windward mark to port, leeward gate (`WINDWARD_LEEWARD_LAYOUT`), one boat, laps loop. A course element may be a `Gate` (`new Gate(markA, markB)` or `{gate: [a, b]}`): one course step whose position for neighbouring legs and the course line is the anchor midpoint. It is *passed* (counts as rounded everywhere) when the net count of crossings of the anchor-to-anchor segment, forward = away from the previous element, is ≥ 1 and the boat is `GATE_PASS_HYST_M` (0.75 m) past the line; unpassed when the count drops to ≤ 0 and she is 0.75 m back. Crossings of the line outside the marks do not count. After passing either gate mark may be rounded. The highlight stays on a passed gate until the boat is 12 m from both gate marks. Gate overlay: dashed gate line (amber when next), green rings on both marks, faint zones, one `NEXT GATE n` / `✓ n` label; info line `Course: next gate n · lap L`. Checks: `scripts/course-check.mjs`, `scripts/gate-check.mjs`. 14 = start procedure (`START_COURSE_LAYOUT`): start line + windward mark + leeward gate, one boat on a port beam reach autopilot below the line. `controls.js` holds `startSequence` (`getStartSequence()`); `main.js` calls `seq.step(simDt)` and `seq.update(players)` once per world step, before course progress, fills `#start_hud` (big mm:ss clock, signal + flag icons, boat status, flash on each signal) and draws `startGuides` for boat 0. Signals at −warning / −prep / −oneMinute / 0: `RRS_START_TIMINGS` 300/240/60 s is the default; scenario 14 uses `COMPRESSED_START_TIMINGS` 60/48/12 s (1/5 scale, X flag max 48 s) with a 2 s lead. Line = anchors of the RC (starboard, east) and pin marks; course side = side holding the windward mark. OCS at the gun: any hull vertex on the course side of the infinite line and within the line span ± `START_OCS_EXT_M` (4 m). X flag while any boat is OCS, max `timings.xFlag` after the gun. Returned = whole hull on the pre-start side (line or extensions). Start = first bow crossing of the segment pre-start → course side after the gun while not OCS; start time interpolated. `new Course(..., {startSequence})` holds progress (`waitingForStart`, text `Course: start first, then mark 1`, no mark highlighted) until `seq.hasStarted(boat)`; courses without one (12, 13) are unaffected. Check: `scripts/start-check.mjs`. Rule 31 (all mark scenarios 11–14): `main.js` calls `recordMarkTouches(players, getMarks(), {simTime, racing})` after `recordContacts`; racing = no start sequence, or `seq.racing` (from the preparatory signal). A touch = planck touching contact or hull-to-buoy gap ≤ `MARK_TOUCH_M` (0.02 m); one touch per contact, re-armed once the hull is > `MARK_TOUCH_REARM_M` (0.25 m) clear of that buoy (a touch before racing also latches, so it is not charged later). Each touch pushes one pending penalty via `chargePendingPenalty` with `{rule: '31', kind: 'mark', reason: 'Rule 31: touched mark 2', label}`; cleared by the usual tack + gybe or Q/E circle (RRS 44.1 One-Turn Penalty). ### Coding conventions for `boltzmann.js`

The LBM implementation is kept as close as possible to the Lagrava paper. Follow these rules when editing:

- **Variable names match paper notation**: `f0, fN, fS, fE, fW, fNE, fNW, fSE, fSW` (Eq. 2), `rho` (ρ), `ux/uy` (u), `nu` (ν), `omega` / `omega_c` / `omega_f` (ω).
- **Equation comments**: every calculation that has a numbered formula in the paper must have a `// Eq. N:` comment on or above it. Current coverage: Eq. 2 (weights), Eq. 3 (equilibrium), Eq. 4/5 (macro fields), Eq. 10 (ω from ν), Eq. 15 (BGK collision), Eq. 16 (streaming), Eq. 24 (fine-grid ω), Eq. 29/30 (non-equilibrium rescaling), Eq. 33 (centered `f_neq` filter), Eq. 34/38/39 (spatial interpolation), §3.5 (sub-cycling and time interpolation).
- **Geographic neighbour naming**: `nbN` = y+1 (north), `nbS` = y−1, `nbE` = x+1, `nbW` = x−1, and diagonals accordingly. Pull-scheme streaming reads from the *upstream* geographic direction (e.g. `fN_in = nbS.fN`).
- **No dead code**: remove stale methods rather than commenting them out.
- **`return` and its expression stay on one line.** A newline after `return` is parsed as `return;`. The left-biased Eq. 39 branch in `_injectGhostCell` (`interpX`, `interpY`, `interpXY`) used to do that, which stored `undefined` velocities on the high-index edge of a refinement domain and, once that domain was stepped, NaN'd the lattice.
- **Eq. 5 divides by rho.** If density collapses (rho ≤ 0) the velocity is NaN and streaming spreads it. `collide` resets that cell to rest equilibrium. Restriction (`_restrictCell`) skips the coarse write when the coincident node is missing or its density or velocity is not finite. Boat forcing is the exact-difference kick (`addMomentum`): it refuses a missing cell, a non-finite force, a collapsed density, or a non-finite result. The previous `setEquil` push (`pushCellVelocity`) capped speed at 0.35 because a pinned sail stacked equilibrium on a cell that did not stream. That cap is not on the exact-difference kick: the kick is streamed, and a fine cell's `1/dx²` sample is larger than 0.35 on purpose.
- **Domain boxes are non-empty integer rectangles.** `addDomain` / `moveDomain` drop inverted or non-finite corners (a boat past the wall, or a NaN body). Level-2 boxes are clamped inside the parent in `main.js`.
- **Sail lookup stops at the last table entry.** `aeroCoefficients` clamps the index so awa = ±180 does not read past the 21-entry lift/drag tables (`undefined * 0` is NaN).

### Visualization Modes

The `plotSelect` dropdown controls what the `DataTexture` displays: density, x-velocity, y-velocity, speed, or curl. The contrast adjustment is applied when painting (`fieldPainter.js`).
- **Overlap sync**: after every root step, `Boltzmann._syncBoatOverlaps()` makes same-depth boat grids that overlap share one flow. Coincident fluid nodes map through an integer lattice offset. The owner is the grid that has its own finer child at that node; if neither or both do, the later boat owns. The other grid copies the owner's populations and macros, and barrier cells are skipped. With one boat it does nothing, so single-boat results are bit-identical. `bm.syncOverlaps=false` turns it off.
- **Fast wind / map size**: `?simRes=2f` uses the 2 m root cell, steps it every frame, and gives velScale = cellSize·stepsPerFrame = 2. **Wind is in m/s everywhere external** (UI, `Boltzmann` ctor, `setWindSpeed`, `Map`, `ConstantWind`, sim `wind` command): lattice U = m/s · Δt / Δx = m/s / (30 · velScale) (`Boltzmann._latticeU`). Old UI wind W = W·0.3 m/s. The felt wind, sail coupling and speed plot are multiplied or divided by velScale, so a given UI wind is the same physical wind on every setting. The stable range is lattice U ≤ 0.25: 15 m/s on 2f. Fast modes floor matchedNu at 0.0125 (`FAST_MATCHED_NU_FLOOR`). UI wind W is advected at 0.3·W m/s (W × 0.583 kn). (True since fixed 30 FPS, one field frame per 30 Hz tick; the old 3-pass app ran 90 frames/s, i.e. 0.9·W m/s.) Real-time ceilings: 1 m 25 → 14.6 kn, 2f 50 → 29 kn, 2f34 ~62 → 36 kn, 4f 100 → 58 kn.
- **Fixed 30 FPS** (PR #48): `SIM_PASSES_PER_TICK` = 1 (main.js; `?simPasses=` still overrides), render capped at `RENDER_FPS` 30 (renderer.js, `window.__renderStats`). boat.js converts the old per-pass tuning (`LEGACY_PASSES_PER_TICK` = 3): blends 1−(1−a)³ (wind α 0.488, penalty 0.834, autopilot lag 0.271), centring cubed, manual rudder rate ×3 (pump from the per-pass step), autopilot KD 100 → 29.9, I decay 0.85³, forces and impulses ×3 (`FORCE_PASSES`; planck accumulates applyForce until world.step). Scenario frame indexes stay in 90 Hz units (sim.js `SCENARIO_FRAMES_PER_TICK` = 3). Curl holds are now a real 0.2 s. The headless harness was always 1 pass per world step, so its pins moved (amr.test bs 2.13 → 2.85); vs the real old app the kick-off boat speed matches to 0.03 % (`scripts/fixed30-compare.mjs`).
- **Default root cell `2f`** (`DEFAULT_SIM_RES`, src/sim-modes.js): 2 m cell, 1 lattice step per tick (velScale 2, 4 refinement levels to 1/8 m, matchedNu floored at 0.0125, root ν 0.025), all map sizes, app and SimCore.
